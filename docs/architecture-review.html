Architecture & framework design — how a Google Apps Script app governs the lifecycle of stale Snowflake data assets, crash-safely.

EDG · Stale Data Monitoring
Say: This is an internal governance app, not a data pipeline. It ingests Snowflake extracts, flags stale assets, and walks each through a governed lifecycle — notify, contest, quarantine, purge — with consolidated Slack notifications. The interesting engineering is doing all this on Apps Script's 6-minute execution limit without ever losing or duplicating work.

Context

What problem it solves

Stale Snowflake tables accumulate cost and risk. This app gives data governance a controlled, auditable way to retire them — with the owners in the loop and platform teams handed clean work.

Ingest

Review extracts

Import complete Snowflake asset extracts; detect assets past the inactivity threshold.

Govern

Drive lifecycle

Notify owners; allow contest / exception / self-purge / restore / admin dismiss.

Hand off

Quarantine & purge

Prepare controlled handoffs for platform teams; record everything in an audit log.

Access is scoped by stewardship & managed team; admins see all. Every status change, comment, notification, and partner action is written to an append-only audit history.
EDG · Stale Data Monitoring
Say: Emphasize governance + auditability. The app is deliberately conservative: PRD is view-only by default, Slack sends are de-duplicated, and platform handoffs are queued (non-dispatching) rather than fired automatically.

Say: Each worker does ~3 batches, stops at 30s, persists its cursor, and reschedules itself. Batch payloads are keyed by runId|cursor, so a re-run replays the saved plan instead of recomputing. After 3 failures it pauses for explicit resume. There's even auto-recovery from Google's 10M-cell limit.

Flow · Reliability

Slack delivery — no duplicate sends

sequenceDiagram
    participant N as NotificationService
    participant R as ReliabilityService
    participant L as Slack_Delivery_Receipts
    participant W as Slack webhook
    N->>R: deliverSlackPayloadOnce_
    R->>L: read entries for recipient/type/ids
    alt existing ATTEMPTING
        R-->>N: throw DELIVERY_UNCERTAIN (block dup)
    else existing ACCEPTED
        R-->>N: return saved receipt (no resend)
    else new
        R->>L: write ATTEMPTING + flush() BEFORE fetch
        R->>W: UrlFetchApp.fetch(payload)
        alt HTTP 2xx
            R->>L: mark ACCEPTED → notifications SENT
        else client-reject 4xx
            R->>L: mark REJECTED (safe retry)
        else other / thrown
            R-->>N: leave ATTEMPTING, throw UNCERTAIN
        end
    end
Admin “Verify uncertain deliveries” resolves stuck rows: RECEIVED → mark ACCEPTED (no resend); NOT_RECEIVED → RETRY_APPROVED (retry allowed).
EDG · Stale Data Monitoring
Say: This is the cleverest part. Delivery intent is written and flushed BEFORE the webhook call. An ambiguous webhook result is never auto-retried (would risk a duplicate) and never dropped — it's parked as ATTEMPTING for a human to verify. This is exactly the "Run next Slack checkpoint" banner behavior.

Framework · Reliability

Why it survives crashes

Write-ahead

Durable write plans

Every mutation is saved as a keyed plan before it's applied, then replayed idempotently on resume.

Double buffer

Recovery sheets

Payloads alternate across Recovery_* slots with a committed pointer — an interrupted write leaves the prior payload readable.

Triggers

Watchdog + replacement

The new trigger is created before the old one is deleted, so a worker never loses its wake-up.

Ledger

Slack delivery receipts

Intent recorded before the side effect; ambiguous results held for human verification, not blind retry.

Operational guardrail: never delete the Recovery_* or Slack_Delivery_Receipts sheets or their Script Properties — they carry in-flight recovery state.
EDG · Stale Data Monitoring
Say: The unifying principle across the whole app: durable intent before side effect. This is what lets multi-minute, multi-sheet workflows run safely under a 6-minute runtime that can be killed at any moment.

Framework · Safety

Environments & security

Environments

DEV & PRD, one workbook

DEV sheets are DEV_-prefixed; PRD is view-only by default. Config/roles/teams shared; lifecycle records isolated. Non-admins are forced to PRD.

Access

Three-tier auth

ADMIN / role user / VIEWER, resolved from shared sheets. Every mutating entry point re-checks server-side; per-record visibility via team rules.

Secrets

Script Properties only

Webhook + action endpoints live in Script Properties, never in source. DEV Slack locked to approved recipients.

Surface

Hardened entry

executeAs: USER_DEPLOYING, domain access; doGet sanitizes deep-link params and escapes template injection.

EDG · Stale Data Monitoring
Say: Safety is layered: read-only PRD, server-side re-auth on every write, recipient locking for Slack, secrets out of source. The blast radius of a mistake is deliberately small.
